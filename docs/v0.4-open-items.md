## A. 事件溯源底座在 v0.4 没有生产调用方【部分订正】

### 先纠正三处旧错误

| 旧说法 | 实际 |
|---|---|
| 「`store.New` 生产零调用方」 | **错**。`internal/wire` 的 `New` 调它（为 `FileStore.ForRun`），这是生产路径 |
| 「`graph.json` 无写入方」 | **错**。装配层的 `dagGraphSaver` 恒写它（`HarnessOptions.Graphs` 由装配层恒提供） |
| 「`RegisterEngine` 唯一调用方是 `contract_test.go`」 | **错**。它现在是**零调用方**（含测试） |

行号整体偏移也一并作废——本文此后不再写行号。

### 仍然成立的：事件溯源那一半

### R1 之后的处置

**v0.3 的三个存储端口已移出根包到 `legacy/`**（`legacy.Store` / `legacy.GraphStore` /
`legacy.EvidenceStore`）。于是「哪些端口是活的」不再需要靠读注释判断——根包里现在
只剩 v0.4 在用的端口。

`store.FileStore` 本身**保留**：装配层仍然 `store.New(...)` 并用它的
`ForRun` / `PutGraph` / `PutGraphExport` 写图。注意这三个方法**本来就在旧 `Store`
端口之外**，所以移出端口不影响这条生产路径。

**「候选明文只活在返回值与私密 trace 里」这句话在 R1 之后不再准确**：v0.5 新增了
私密候选审计 `<ResultDir>/private/<runID>/submissions.jsonl`，由
`store.ResultFileStore.AppendAudit` 写（生产路径，已接线）。也就是说「提交过哪些
候选、平台怎么判的」这个问题**现在有答案了**——它此前是本文最尖锐的一条缺口。

`Append` 的「先写事件、再原子写快照」顺序**仍是 `store.Append` 的硬契约**（由注入
快照写失败来测），只是当前没有调用方。

## B. v0.3 引擎注册表【已消解】

`Engine` / `Options` / `New` / `RegisterEngine` / `RunHandle` 已全部移出根包到
`legacy/`。并且有一条现在写明了的结论：

> **那个注册表从来没有被填充过。** `engine/` 目录不存在，`RegisterEngine` 零调用方，
> 所以 `legacy.New` 的默认实现（「引擎实现未注册」）是**唯一可达**的结果。

保留它们是因为删掉是公开 API 的破坏性变更，不是因为它们在工作。这一点写进了
`legacy/engine.go` 的注释——旧注释声称「CLI 与 example 都会走 `harness.New`」，
那句话早已失效（CLI 走 `internal/cli` → `internal/wire` → `harness.NewHarness`）。

## 怎么防止再漂移

拓扑提取脚本是可重跑的，且**每条动态边都带源码证据模式**，失配会当场报警：

```bash
python3 analysis/red-harness/extract_topology.py     # 重算 topology.json + 三份 .mmd + 摘要
```

它回查 dispatch 边（`cli.SetWire`、`SandboxSession`、`EvidenceStore`、
`sys.modules.setdefault` 等）在源码里是否仍然成立。**R1 移出 `Store`/`GraphStore`/
`EvidenceStore` 之后，脚本的证据模式已同步改指 `legacy/`**——它是这次改动里最容易
被漏掉的连带项，因为失配的形态是「脚本自己报警」，而不是编译失败。

它**不会**自动发现新的漂移——只在已知边失效时报警。新增公开端口或改变装配方式后，
应把新边补进脚本的 `DISPATCH_EDGES` / `RUNTIME_EDGES`。

另有一条**不靠脚本**的防线：`legacy/layering_test.go` 用 `go/parser` 扫全仓 import
图，断言「根包零内部依赖」「legacy 只 import 标准库与根包」「实现包两两零边」
「同时 import ≥2 个实现包的只有 `internal/wire`」。这四条此前只写在 CLAUDE.md 里，
靠人读——文档不会因为一次 `import` 变红。
