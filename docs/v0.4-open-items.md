## 怎么读

v0.4 是破坏性升级：`docs/PLAN v0.4.md` 明确**不实现**暂停恢复、control socket、Web、
公开报告和事件重放。所以下面一部分条目**是设计决定的结果，不是缺陷**。

判断标准只有一条：**这个派生物是否还在公开面 / 文档 / 注释里被当作生效的东西描述。**

- 在 ⇒ 是**漂移**，会误导人，要修。
- 不在 ⇒ 只是可清理的死面，排期随意。

按这条标准，A 与 D 是漂移，B 已消解，C 是死面。
E 不属于这四类：它是一个**机制成立、但今天没有生产触发路径**的隐患，按「不在」处理，
但附了一条「什么会把它变成『在』」的说明。

## A. 事件溯源底座在 v0.4 没有生产调用方【部分订正】

| 「`store.New` 生产零调用方」 | **错**。`local` 的 `New` 调它（为 `FileStore.ForRun`），这是生产路径 |
| 「`graph.json` 无写入方」 | **错**。装配层（`local`）的 `dagGraphSaver` 恒写它（`HarnessOptions.Graphs` 由装配层恒提供） |

### R1 之后的处置

**v0.3 的三个存储端口已移出根包到 `legacy/`**（`legacy.Store` / `legacy.GraphStore` /
`legacy.EvidenceStore`）。于是「哪些端口是活的」不再需要靠读注释判断——根包里现在
只剩 v0.4 在用的端口。

`store.FileStore` 本身**保留**：装配层仍然 `store.New(...)` 并用它的
`ForRun` / `PutGraph` / `PutGraphExport` 写图。注意这三个方法**本来就在旧 `Store`
端口之外**，所以移出端口不影响这条生产路径。

**「候选明文只活在返回值与私密 trace 里」这句话在 R1 之后不再准确**：v0.5 新增了
私密候选审计 `<ResultDir>/private/<runID>/submissions.jsonl`，由
`store.ResultFileStore.AppendAudit` 写（生产路径，已接线）。也就是说「提交过哪些
候选、平台怎么判的」这个问题**现在有答案了**——它此前是本文最尖锐的一条缺口。

`Append` 的「先写事件、再原子写快照」顺序**仍是 `store.Append` 的硬契约**（由注入
快照写失败来测），只是当前没有调用方。

## D. 回收报告的「按 reason 分解」没有落点【漂移：注释承诺的比落点给的多】

`harness.ReclaimReport.Pending` 的字段注释写着「发现了但没删的资源，**待人工处置**」，
而生产路径上没有任何地方能让人处置它——唯一的读取点把它折成了一个整数：

| 位置 | 事实 |
|---|---|
| `harness/reclaim.go` | `ReclaimReport` 有两个集合：`Reclaimed []RunID` 与 `Pending []StaleObject`；`StaleObject` 带 `Kind` / `RunID` / `Owner` / `Reason` |
| `v04.go`（`reclaimStale` 之后） | **唯一读取点**：`result.PendingStale = rep.PendingTotal()`。明细在这里就死了 |
| `store/results.go` 公开面 | `reclaimedStale` / `pendingStale`，两个 `int`。没有第三种落点 |
| 其余 `.Pending` 命中 | **全部在 `_test.go` 里**（`executor/reclaim_test.go`、`executor/docker_test.go`、`executor/session_integration_test.go`、`identity_test.go`）。核实命令：`grep -rn "\.Pending" --include=*.go .` |

**为什么现在才值得记**：`PendingTotal()` 把三个语义完全不同的 `StaleReason` 折成一个数：

| Reason | 含义 | 操作上该不该管 |
|---|---|---|
| `owner_mismatch` | 别人的部署正在用的资源 | 共享宿主上**正常**，忽略 |
| `owner_unknown` | 没有 owner 标签的旧资源 | 删不掉（fail closed，正确），但不必紧张 |
| `unparsable` | **扫描器无法归属这个对象** | **这是警报** |

在 `3d3d299` 修好回收扫描**之前**，扫描器的输出格式是坏的（`{{json .Labels}}` 打印的是
逗号拼接的字符串、不是 JSON 对象），于是**每个对象**都落进 `unparsable`——那个计数恒等于
「全部」，是废的，看不出任何东西。修好之后计数才有意义，而这时真正携带信号的是**三个原因
的分解**：`unparsable` 不再是常态，它的含义收窄成「`docker inspect` 的字段位变了，或某个
标签值真是空串」——也就是**同一个失效形态（扫描器坏了）在计数上与「别人在跑」一模一样**。

**准确的缺口描述（不要写成「Pending 不可见」）**：`Pending` 作为**计数**是可见的。缺的是
**按 reason 的分解**——公开面把「正常」与「扫描器坏了」平均成了同一个数，而明细面
（`Kind` / `RunID` / `Owner` / `Reason`）在 `v04.go` 那一行就死了，没有任何私密面或日志写者。

**处置：只记录，不修。** 这是公开面新增字段，不在本轮冻结契约里，按仓库纪律不顺手补全。
`Pending` 的明细是**本机资源拓扑**，进公开面等于把它拷进会被转发、归档、贴工单的结果里；
正确的修法是补一个私密面或日志写者，那是一次独立设计，不是加一行。

## E. `uninstallRulesByRun` 按子串认规则【隐患：机制成立，今天只有非生产入口能触发】

`executor/reclaim.go` 的删除路径这样认领规则（注释里带 owner 是有意的，理由见
`commentFor`）：`comment := commentFor(owner, runID)`，形态 `<前缀><owner 指纹>-<净化的
runID>`，然后逐行 `if !strings.Contains(line, comment) { continue }`。

**`Contains` 在这里应当写作「精确相等」。** 同一 owner 下若同时存在两条互为前缀的
runID 规则（`run-1` 与 `run-12`），清 `run-1` 会把 `run-12` 的规则一并删掉——而被删的
正是**另一次运行正在依赖的默认 DROP**。失效方向是「隔离被静默撤掉」，不是「规则残留」；
后者只会漏资源，前者会让一个正在跑的进攻性工具进程突然拥有直连能力。

⚠️ **但它的触发条件今天在生产路径上不成立。这一条必须连着下面一起读**，否则会把一个
不可达的形态读成现役缺陷：

| 事实 | 依据 |
|---|---|
| 生产 runID 由根包生成，形态恒为 `run-<UnixNano>` | `v04.go`（`RunID(fmt.Sprintf("run-%d", started.UnixNano()))`） |
| `UnixNano` 在 2262 溢出前恒为 **19 位**，所以生产 runID **两两等长** | — |
| 等长 ⇒ 互为前缀当且仅当相等 ⇒ `Contains` 退化成精确比较 | — |
| 经过 `Harness.Run` 时 `SandboxSpec.RunID` 被**无条件覆盖**成上面那个生成串 | `v04.go` 的 `sb.RunID, sb.Target = runID, target` |
| `SandboxSpec.RunID` 本身由调用方填，且只校验非空 | `executor/session.go` 只查 `strings.TrimSpace(...) == ""` |
| 陈旧扫描路径确实会走到它：`ReclaimStale` → `Reclaim(ctx, id)`，`id` 读自容器标签 | `executor/docker.go` |

所以可达入口只有一个：**调用方直接驱动 `Sandbox` 端口并自选 runID**（`run-1` / `run-12`）。
这不是臆想的用法——`executor/spec.go` 的注释本身就把「两个部署各自开一个 `run-1`」当成
合法形态。只是那两个 `run-1` 的 owner 指纹不同、互相分得开；**同一个部署内**的
`run-1` 与 `run-12` 则分不开。

**处置：只记录，不修。** 修法是明确的——把 `--comment` 从 `iptables -S` 的行里解析出来
后精确比较，替换掉子串匹配——但它属于 `executor` 的独立一轮，且**当前没有已知的可触发
路径**：为一个不可达的形态去改删除路径的匹配方式，风险大于收益。

⚠️ **什么会把它变成可达**：任何让 runID 不再是「等长纳秒串」的能力——「调用方指定
runID」、「崩溃续跑沿用旧 runID」、或把 `SandboxSpec.RunID` 的校验放宽到接受短名。
落地这类能力时**必须先修这一条**，否则新功能会以一个静默撤掉隔离的方式生效。

## 怎么防止再漂移

拓扑提取脚本是可重跑的，且**每条动态边都带源码证据模式**，失配会当场报警：

```bash
python3 analysis/red-harness/extract_topology.py     # 重算 topology.json + 三份 .mmd + 摘要
```

它回查 dispatch 边（`cli.SetWire`、`SandboxSession`、`EvidenceStore`、
`sys.modules.setdefault` 等）在源码里是否仍然成立。**R1 移出 `Store`/`GraphStore`/
`EvidenceStore` 之后，脚本的证据模式已同步改指 `legacy/`**——它是这次改动里最容易
被漏掉的连带项，因为失配的形态是「脚本自己报警」，而不是编译失败。

它**不会**自动发现新的漂移——只在已知边失效时报警。新增公开端口或改变装配方式后，
应把新边补进脚本的 `DISPATCH_EDGES` / `RUNTIME_EDGES`。

另有一条**不靠脚本**的防线：`legacy/layering_test.go` 用 `go/parser` 扫全仓 import
图，断言「根包零内部依赖」「legacy 只 import 标准库与根包」「实现包两两零边」
「同时 import ≥2 个实现包的只有 `local`」（`assemblyPkgs` 已是单元素集合，N0.1 的迁移
窗口关闭后 `internal/wire` 没有任何 import 方）。这四条此前只写在 CLAUDE.md 里，
靠人读——文档不会因为一次 `import` 变红。
