# v0.4 未接线代码面（open items）

> 更新：2026-09-22。本文由依赖/拓扑提取发现（`analysis/red-harness/`，脚本可重跑）。
> 每条都带 `file:line` 证据，并标明「这是设计决定还是要修」。

## 怎么读

v0.4 是破坏性升级：`docs/PLAN v0.4.md` 明确**不实现**暂停恢复、control socket、Web、
公开报告和事件重放。所以下面一部分条目**是设计决定的结果，不是缺陷**。

判断标准只有一条：**这个派生物是否还在公开面 / 文档 / 注释里被当作生效的东西描述。**

- 在 ⇒ 是**漂移**，会误导人，要修。
- 不在 ⇒ 只是可清理的死面，排期随意。

按这条标准，A 与 B 是漂移，C 是死面，D 已修。

## A. 事件溯源底座在 v0.4 没有生产调用方【漂移】

`store.FileStore`（事件日志 / 原子快照 / 候选账本 / 图载荷）在生产路径上**从未被构造**——
唯一构造点是它自己的测试。

| 符号 | 位置 | 生产调用方 |
|---|---|---|
| `store.New` | `store/store.go:107` | 无（仅 `store/store_test.go:24,824,852`） |
| `harness.Store` | `ports.go:382` | 无 |
| `harness.GraphStore` | `ports.go:373` | 无 |
| `harness.EvidenceStore` / `FileStore.Private()` | `ports.go:392` / `store/store.go:456` | 无 |
| `dag.Graph.Save` / `Load` / `LoadOrNew` | `dag/store.go:57,182,252` | 无 |
| `store.PutReport` | `store/store.go:229` | 无（仅 `store/store_test.go`） |

落点层面的后果：

| 落点 | v0.3 角色 | **v0.4 现状** |
|---|---|---|
| `<StoreDir>/runs/<id>/events.jsonl` | 领域事件日志，序号单调 | **无写入方** |
| `<StoreDir>/runs/<id>/run.json` | 原子快照，恢复基线 | **无写入方** |
| `<StoreDir>/runs/<id>/graph.json` | DAG 载荷 | **无写入方** |
| `.../private/candidates.jsonl` | 候选明文账本 | **无写入方** |
| `.../private/evidence/` | 原始工具输出（含明文） | **无写入方** |
| `.../report.json` / `report.md` | 公开报告 | **无写入方**（`report/` 包不存在） |
| `<ResultDir>/results/<runID>.json` | 公开指标 | **有**（`store/results.go:350`） |
| `<ResultDir>/private/<runID>/<题目哈希>.jsonl` | — | **有**（`store/trace.go:21`） |
| `<StoreDir>/run.lock` | 跨进程单运行锁 | **有**（`internal/wire/lock.go`） |

### 为什么这是漂移而不是无害死面

CLAUDE.md 与 `docs/architecture.md` §4 都把 `private/` 描述成候选明文的落点，而 v0.4 的
私密面实际是 `<ResultDir>/private/`（trace 汇）。

**明文纪律本身没有破**——trace 目录同样是 0700/0600，`ResultFileStore` 也从不 marshal
`OutcomeView`/`Candidate`/`Flags`。但**机制与文档不一致**：照文档去找 `candidates.jsonl`
的人会找不到，而最可能的误判是「候选明文根本没落盘」或「私密面没生效」。

### 要决定的

1. 候选账本在 v0.4 是**有意去掉**，还是**漏接**？
   - 有意 ⇒ 把 `harness.EvidenceStore` 与 `store/private.go` 显式标注为 legacy，
     并把「候选明文只活在返回值与 trace 里」写进 `architecture.md` §4。
   - 漏接 ⇒ 这是一条真实的缺口：v0.4 没有任何地方留存「提交过哪些候选、平台怎么判的」，
     而 v0.3 的账本正是为回答这个问题建的（追加日志，崩溃后可答）。
2. `Store` / `GraphStore` / `EvidenceStore` 三个端口若确定不再使用，是否移出根包？
   根包公开面越小，「哪些端口是活的」越不容易误读。

## B. v0.3 引擎注册表零生产调用方【漂移】

```
harness.New        engine.go:79
  └─ newEngine     engine.go:97   ← 包级变量，默认返回「引擎实现未注册」
       └─ RegisterEngine  engine.go:109
```

v0.4 的 `NewHarness`（`v04.go:309`）**直接构造** `*Harness`，不经过注册表。
`RegisterEngine` 全仓唯一调用方是 `contract_test.go:370,397`。

`docs/architecture.md` 开头说「旧 Engine、RunHandle 和事件快照仍在源码中供 v0.3 读取与
测试使用」——保留的理由成立，但**没有任何文档写它计划何时退场**，也没写「新代码不要
再往这条路上加东西」。

**要决定的**：`Engine` / `RunHandle` / `New` / `RegisterEngine` 的退场条件与时间点。
（CLAUDE.md 已加了一条「不要再往那条路上加东西」的提醒，但那只是止血。）

v0.4 明确不做公开报告与 Web（`docs/PLAN v0.4.md`）。`store.PutReport` / `ReportPath`
属于同一类死面，见 A 表最后两行。

**要决定的**：`store` 里的报告路径常量与 `PutReport` 是否一并标注 legacy。
这条不急——它不误导人，只是占位。

## 怎么防止再漂移

拓扑提取脚本是可重跑的，且**每条动态边都带源码证据模式**，失配会当场报警：

```bash
python3 analysis/red-harness/extract_topology.py     # 重算 topology.json + 三份 .mmd + 摘要
```

它回查 11 条 dispatch 边（`cli.SetWire`、`SandboxSession`、`EvidenceStore`、
`sys.modules.setdefault` 等）在源码里是否仍然成立。它**不会**自动发现新的漂移——
只在已知边失效时报警。新增公开端口或改变装配方式后，应把新边补进脚本的
`DISPATCH_EDGES` / `RUNTIME_EDGES`。
